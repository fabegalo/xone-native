# M0 — architecture decision and reproducible evidence

Status: **host-side image inspection only; no SystemOS executable code has been launched**.

## Verified upstream facts

- Xbox One Research: HostOS manages VMs and hardware; SystemOS hosts the original graphical shell and system applications, using an Xbox-specific OneCoreUAP environment in later revisions; GameOS/ERA is separately launched for XDK titles.
- The documented SystemOS disk mapping includes `system.xvd` (C:, read-only), `systemaux.xvd` and `systemauxf.xvd` (inbox apps), `settings-saved.xvd`, `systemmisc.xvd`, and user storage. This is not a ready-to-boot set of ordinary PC files.
- XVD is a signed, hashed and potentially encrypted container. Header recognition is not authentication and does not grant access to its contents.
- Documented ERA launch sequence uses SystemOS `eraproxyapp.exe`/`eracontrol.exe`, `xvmctrl.sys` and HostOS coordination with GameOS `xamss.exe` / `comsrvhost.exe`. Launch-from-dashboard requires much more than a PE loader.
- Source inspection of WinDurango `projects/WinDurango.KernelX/src/kernelx.cpp`, `projects/WinDurango.WinRT/src/WinDurangoWinRT.cpp`, `projects/WinDurango.D3D11X/src/d3d11.x.cpp` and CMake: separate DLLs for game-facing compatibility, with Windows-specific APIs. It has a different target than original SystemOS boot and has LGPL-3.0 licensing.
- Official Azimuth page describes direct execution of original game code with Xbox WinRT→Win32 and D3D11.X→D3D12 translation. It does not claim SystemOS/dashboard support and its source is not public.

## Provisional version strategy

**10.0.10586.1029 is a documented inspection reference**, not a proven bootable, easiest or recommended release: Xbox One Research's XBFS page provides a dated mapping of its `system.xvd`. Choosing the actual first SystemOS target **requires lawful, readable input and concrete binaries/dependency data**. Do not mistake a header's required-version field for a successful OS-version identification. Earlier and newer shell generations may use different Windows app models and layouts. Never mix system files across incompatible revisions.

## Validated common architecture and incremental migration

Maintainer validated this boundary and migration in chat on **2026-11-07**: use the same modules and lifecycle as x360-native, preserving Xbox One contracts rather than importing PowerPC/XAM contracts. This supersedes the provisional hybrid diagram; it does not select a VM, translation strategy or service implementation.

| Common module | Existing implementation and remaining work |
| --- | --- |
| Management launcher | `src/main.cpp` and `src/bootstrap_main.cpp` provide management CLIs; neither replaces the original dashboard. |
| Content/catalog | `inspection.cpp`, `inventory.cpp`, `tools/study_update_zip.py` and `tools/systemos_preflight.py` inspect and identify revision-bound content without requiring copies. The Python archive adapter uses the C++ inspector; it is not another PE loader. |
| Preparation/native execution | `bootstrap.cpp::Session` audits profiles/dependencies and launches a limited Windows AMD64 contract using the host loader. AppModel parsing/activation stays in `appmodel*.cpp`. Private Xbox modules, cross-ISA translation/AOT and execution on other hosts remain unimplemented. |
| Compatibility runtime + explicit HLE | `compatibility.h/.cpp` owns service requirements, parsing and domain-specific missing-provider diagnostics; preparation and pre-launch revalidation use it. There are **no Xbox service providers yet**. HostOS, SystemOS, GameOS/ERA and GameCore are distinct contract domains; the current SystemOS profile selects only SystemOS. |
| Original GPU / Native GPU | Both must use the same guest contracts, synchronization and logical console state. `Presenter`/D3D12 is host presentation and `FramePipe` is desktop CPU frame transport. Neither is a working Xbox GPU backend; original composition, shared GPU surface transport, Vulkan and Metal remain gaps. |
| Original system/games | Original dashboard → library → game → Guide/dashboard remains the product flow. No original SystemOS execution, game support or authentic frame has been demonstrated. |
| Session supervisor / host adapters | Existing process lifecycle, AppModel observation and platform I/O are reusable pieces. Original system/game transitions, Guide routing, recovery and coordinated persistent state remain missing. |

The runtime must own one coherent console state for activation, memory, threads, timing, users, storage, audio, input and graphics, shared by both GPU paths. Those owners and their Xbox APIs are implementation gaps, not supplied by `CreateProcessW`, AppModel or frame transport. Implement each service from an observed, revision-bound dependency with focused regression evidence; do not create success stubs or a second runtime/loader. HLE does not replace original UI/assets. Original firmware services, selective HLE and hybrid service implementations remain alternatives to validate per concrete contract.

Reuse direct execution where ISA, ABI and dependencies are demonstrated; evaluate AOT/translation where needed. Kernel/device requirements now report `service_adapter_missing`, preserving domain and evidence, rather than asserting `isolated_backend_required_for_evaluation`. That diagnostic change does not make the dependency executable. A VM/hypervisor requires concrete dependency evidence and a separately validated implementation choice. Windows/Linux/macOS x64/ARM64 remain targets, including Steam Deck on Linux and Intel/Apple Silicon on macOS; current builds do not certify their Xbox runtime. No unnecessary recompilation or global AVX2 requirement.

Next migration steps: retain the existing catalog/preparation/activation/presentation contracts, obtain a readable original component set, audit its service/API and composition dependencies, then implement and validate the smallest observed contract through this boundary. Keep the existing Win32/AppModel paths until an approved replacement is verified. Positive AppModel activation still requires an authorized disposable guest; no host registration, policy/certificate changes or silent fallback.

## Exact blockers before the first authentic SystemOS frame

1. Obtain a **lawfully accessible, readable** SystemOS shell/component executable and its matching assets without bypassing encryption/DRM. A raw `system.xvd` header alone is not enough. Cannot determine the first specific dashboard build solely from public disk-layout docs.
2. Resolve complete image dependency graph: PE imports, package/activation metadata, runtime DLLs, WinRT factories, capability requirements, services, resource and volume mapping. The M0 inspector starts this graph when given a readable PE.
3. Determine whether the target component depends on OneCoreUAP kernel services, secure boot/CI, win32kmin, Xbox window manager, app model, composition, XVIO or other unavailable virtual devices. Compare native-hosted, HLE, original-firmware, translation and isolated execution options against each observed contract; do not infer a VM requirement from a service category.
4. Implement the minimum faithful app activation, composition/presentation and input behavior necessary to draw the **component's own** first frame, not a surrogate window. Record component hashes, environment, exact build, and screen capture only after observing authentic code execution.

## Local M0 validation and nonclaims

`xone-native inspect` is implemented in C++20 and uses a bounded, offset-checked reader without creating any additional copy of source files. Tests use synthetic PE and XVD headers, not Microsoft binaries. The CLI prints explicit unverified metadata. Unit tests cover valid fixtures, imports, wrong architecture, missing file, malformed RVA, truncated XVD and unchanged input. GitHub Actions config compiles/tests on Windows, Linux and macOS; matrix success does **not** mean the Xbox One OS works on those hosts or that ARM64 has been validated.
